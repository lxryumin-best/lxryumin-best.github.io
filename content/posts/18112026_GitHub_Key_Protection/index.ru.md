**Контекст (Бизнес-задача / Проблема):**
Недавно я подключил ИИ-ассистента к GitHub-репозиторию этого портфолио. Теперь он может подготовить статью, положить её в структуру Hugo, собрать сайт и опубликовать. Первый вопрос был не «что он умеет писать», а «до чего он может дотянуться».

Ключ GitHub — не пароль. Это переданные полномочия. Личный токен с широкими правами читает все приватные репозитории, которые видит владелец, переписывает ветки и пушит код, который выполнится в CI. Deploy key даёт меньше прав, но неправильное хранение это не исправляет. У публичного портфолио радиус поражения небольшой. Дело не в портфолио: тот же подход в клиентском репозитории превращает удобную автоматизацию в инцидент цепочки поставок.

Каждая автоматизация добавляет учётные данные. Каждые учётные данные добавляют путь, на котором не нужен человек. Цель не в том, чтобы больше доверять ассистенту. Цель — сделать ключ настолько маленьким, чтобы доверие не было единственным контролем.

**Архитектура и Реализация (Решение):**
Я использую шесть уровней защиты. Ни один из них не экзотический. Ценность в том, что все они применены к одному небольшому процессу.

**1. Выбирайте самый узкий тип ключа.**
Классический personal access token действует на весь аккаунт. Fine-grained token можно ограничить выбранными репозиториями и правами. Deploy key — один репозиторий. GitHub App — одна установка. OIDC вообще убирает долгоживущий секрет из облачных деплоев. Для ассистента, который только публикует статьи, достаточно deploy key с записью в один репозиторий. Отдавать ему токен на весь аккаунт незачем. Классический токен к тому же живёт дольше самой задачи и плохо ограничивается одним репозиторием.

**2. Разделите чтение и запись.**
Читать публичный репозиторий дёшево и почти безопасно. Запись — там, где возникает ущерб. В этой схеме ассистент читает репозиторий через публичный API и пишет ровно через один канал — SSH-ключ на один репозиторий. Нет второго пути записи, нет токена в env-файле, нет «на всякий случай». Один канал проще контролировать, чем пять. Если ассистенту нужен только текст, ему не нужны права на Actions, issues и настройки репозитория.

**3. Держите приватный ключ вне синхронизируемой папки.**
Рабочая папка проекта зеркалируется в облако. Это удобно для черновиков и плохо для секретов. Приватный ключ лежит в отдельном каталоге вне синхронизации, права `600`. SSH-конфиг применяет его только к `github.com`. В `.git/config` репозитория токена нет. Если ключ попал в заметку, чат или коммит — он уже скомпрометирован, считайте так.

**4. Сделайте ключ скучным.**
Один репозиторий, одна задача, одно место. Назовите ключ по процессу, а не по человеку. Запишите, зачем он нужен и когда его последний раз проверяли. Ключ, который отзывается в один клик, можно позволить себе потерять. Раз в квартал проверяйте список deploy keys и токенов: доступ, которым не пользовались полгода, скорее всего уже не нужен.

**5. Поставьте фильтр перед публикацией.**
Права доступа решают, кто может пушить. Они не ловят пароль, вставленный в статью. Перед сборкой Hugo валидатор ищет в тексте литеральные секреты и IPv4-адреса и останавливает пайплайн. Правило намеренно грубое: если текст похож на секрет, сборка останавливается. Это не замена secret scanning. Это последняя дешёвая проверка перед публикацией. Валидатор не понимает контекст и иногда останавливает безобидную строку. Это приемлемая цена: ложное срабатывание дешевле утечки.

**6. Спланируйте утечку заранее.**
Порядок важен. Сначала отзовите ключ, потом разбирайтесь. Если секрет попал в историю git, отзыв останавливает кровотечение, а очистка истории через `git filter-repo` не даёт следующему читателю найти его. Форс-пуш очищенной ветки и проверка журнала безопасности. Потом запишите, что произошло. Ключ, который сменили после инцидента, — урок. Ключ, который сменили заранее, — процесс.

Со стороны GitHub стоит включить даже для личного репозитория: secret scanning и push protection, минимальные `permissions` в workflow Actions, запрет выводить секреты в логи, сторонние actions — на конкретный commit SHA. Ни один пункт не достаточен сам по себе. Вместе они сокращают число способов, которыми одна ошибка становится публичным инцидентом.

**Бизнес-результат (Ценность):**
Ассистенту не нужен был мой аккаунт. Ему нужен был один репозиторий, один канал записи и понятная граница. В итоге публикация проверяется за несколько минут: один deploy key, один валидатор, одна кнопка отзыва.

Это тот же стандарт, который я хочу применять в клиентской инфраструктуре. Начинайте не с «что ещё может эта автоматизация», а с «какой самый маленький ключ всё ещё решает задачу». Ключ, который не дотянется до базы клиента, облачного аккаунта или второго репозитория, можно отдать агенту и спать спокойно.

Доверие — не средство контроля. Средство контроля — область действия.
